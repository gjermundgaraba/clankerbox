Codebase field guide / 01 / Big picture

Clankerbox is the machine layer.

It gives coding tools long-lived Linux and macOS machines: create one, connect to it, keep its workspace, and branch or restore it when supported.

Not an agent framework or a desktop UI. Applications such as Clankerdesk sit above it; VM engines sit below it. The current code also supplies guest-owned terminal sessions.

The organizing idea: keep durable intent in the controller, VM execution on the host, and live terminal state inside the guest.
01

Six words unlock the system

WHERE

Host

A configured computer that runs VMs. It advertises supported profiles and CPU/RAM capacity.

WHAT KIND

Profile

A pinned recipe: OS, architecture, VM engine, image and resources. Capabilities follow runtime support.

YOUR WORKSPACE

Machine

An identified VM on a host, with a retained disk. Stop/start keeps files; it is not process continuation.

WORK IN PROGRESS

Operation

A durable record of a lifecycle request. Acceptance is not completion; callers can inspect its eventual outcome.

RECOVERY POINT

Checkpoint

An explicit artifact restored into a new machine. Linux can retain RAM; macOS uses stopped-disk copies.

LIVE INTERACTION

Session

A guest-owned terminal process, PTY and terminal state. It outlives a viewer or controller connection.

Fork ≠ checkpoint: a fork creates a child machine directly; a checkpoint creates a recovery artifact for later restores. Linux live forks continue RAM on supported profiles. Mac branches require a stopped source. Neither is an operational backup service.

02

Four binaries, three places

Read left to right for orchestration, then down the host column for execution. Boxes inside a zone live in that location.

Follow one request: clankerbox create dev

  1. Client submits. Resolve profile/host and send a lifecycle request.
  2. Controller records. Validate capacity, persist an operation, then dispatch queued work.
  3. Host executes. Journal intent, call the runtime, prepare access and return observations.
  4. Controller completes. Commit the result; the CLI polls the operation until its wait ends.

Why two journals? The controller knows what was requested; the host knows what local work it attempted. A broken SSH connection does not prove the VM operation failed. Ambiguous work can remain unresolved instead of being blindly replayed.

03

Managing a machine ≠ using it

The lifecycle queue above changes machines. These two streaming paths let applications use a running, prepared machine.

Files survive stop/start

The retained disk belongs to the machine. Stopping is not deleting, and connecting does not implicitly start it.

Terminals survive disconnects

Guest sessions retain PTYs, Ghostty terminal state and bounded output. Ordinary SSH alone does not provide this contract.

Reboot is a different failure

Guest sessions do not survive a daemon exit or guest reboot. Controller reconnection is not host-loss recovery.
