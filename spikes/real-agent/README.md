# Real Codex CLI RAM-fork harness

This is a standard-library Python controller for **one actual `codex app-server`
process using its original stdio pipes**. The VM runner must snapshot and restore
the complete live VM. The harness never calls `thread/fork`, `thread/resume`,
history injection, token refresh, purchases, or credit reset endpoints. It never
restarts app-server or reconnects its stdio transport. New Unix-socket *controller
clients* are expected and do not reconnect Codex.

## Guest setup

1. In a fresh Linux VM create an isolated OS user `agent` with its normal
   `/home/agent` home. Provision only the authorized ChatGPT credential into its
   private `.codex` directory. Do not copy user config, hooks, plugins, skills,
   MCP settings, repositories, or Desktop state. The runner owns authentication;
   this harness does not read auth files. Run as this OS user with its ordinary
   login environment. Do not override `HOME` or `CODEX_HOME`.
2. Copy `guest.py`, `client.py`, and `fixture/` into `/opt/real-agent`; make the
   fixture writable by `agent`. Install the actual Linux Codex CLI 0.153.4 as
   `/opt/real-agent/runtime` using the **complete version-matched package**,
   including `bin/codex-code-mode-host`, `codex-package.json`, resources and
   bundled PATH tools. Symlink `/opt/real-agent/codex` to `runtime/bin/codex`.
   A standalone Codex binary authenticated successfully but exposed no usable
   shell tools in the initial Cocoon runs. Initialize the fixture as a local Git repository if
   required by guest tooling; do not commit agent work.
3. Start once as `agent`, preferably under a service with `Restart=no`:
   `python3 /opt/real-agent/guest.py serve --socket /tmp/real-agent.sock --workdir /opt/real-agent/fixture --codex /opt/real-agent/codex --isolated-user agent`.
   It prints only a bounded ready/error object. Core dumps are disabled.
   Standard proxy environment variables are preserved for an owned model proxy.
4. Send `python3 /opt/real-agent/client.py baseline`. It checks `account/read`
   with `refreshToken:false`, requires ChatGPT login, creates one thread with
   the CLI's default model, and performs one authenticated model/tool turn.
   `ok:true`, `state.baseline.idle:true` is the idle snapshot checkpoint.

The thread uses `approvalPolicy:never` and the installed schema's
`sandbox:danger-full-access` inside this disposable VM. Only its fixture is in
task scope. This avoids nesting a kernel sandbox inside a test VM that may not
provide the required features. No model is explicitly selected; the effective
model from `thread/start` is included in reports. Parent and all children share
the same inherited Codex auth state; managed Codex may automatically refresh
credentials as part of normal operation, but this harness never requests refresh.

## Idle checkpoint acceptance

1. Save the complete running VM RAM+disk checkpoint after `baseline`; restore
   two independent children and keep the source parent running. Repair only
   guest network identity if needed; never restart Codex, its controller, shell
   processes, or their inherited pipes. Preserve runner snapshot provenance.
2. In each VM call `client.py branch --name parent`, `--name child-a`, or
   `--name child-b`. Each makes one tiny distinct formula change and runs tests.
   Record host monotonic timestamps after each successful write acknowledgment.
3. Only after **all three write acknowledgments**, run `client.py followup`
   in all three VMs. It asks the same inherited conversation to recall both the
   common pre-snapshot marker and its own post-snapshot marker, without tools.
4. Only after all writes, run `client.py report` in each VM and save the JSON.
   Reports run deterministic fixture tests and hash the final source. Record
   host monotonic timestamps immediately before these reads.
5. Evaluate with
   `python3 evaluate.py parent.json child-a.json child-b.json --ordering ordering.json`.

`ordering.json` is runner evidence, not generated by the guest:

```json
{
  "clock": "host-monotonic",
  "ramSnapshotVerified": true,
  "writesCompleted": {"parent": 10.0, "child-a": 12.0, "child-b": 14.0},
  "readsStarted": {"parent": 15.0, "child-a": 16.0, "child-b": 17.0}
}
```

The three formulas are `2*x+11`, `3*x+17`, and `5*x+23`. The code/test outputs
and remembered branch markers must remain independent even though the app-server
PID/start ticks, controller PID/start ticks, pipe inode numbers, session ID,
thread ID, and original RAM marker match. The installed version exposes session
ID; if a version does not, reports explicitly say `sessionEvidence:unavailable`
and acceptance compares the inherited thread without inventing a provider session.
The RAM marker is generated before
spawning Codex; only its hash is reported. It is not memory-locked, so disable
guest swap if treating it as strict RAM-only evidence. The existing acceptance
sentinel's locked marker can supply that stronger check alongside this harness.

## Optional active builtin-shell checkpoint

Use a **fresh baseline source** (or a VM restored from the idle checkpoint),
before branch writes. A second snapshot family is needed; do not use a source
whose branch has already been assigned.

1. Call `client.py barrier-start`; poll `client.py status` until
   `barrierWaiting:true`. Codex has actually started `python3 barrier.py` using
   its builtin shell. The helper is blocked in a live process. Record the
   waiting helper PID/start ticks and marker hash; snapshot that live VM.
2. In parent and both children call `client.py barrier-release --name NAME`,
   then `client.py barrier-wait`. The original helper reads its branch's local
   release file, writes its independent result, and lets the same real Codex
   turn continue. No tool or app-server process is restarted.
3. Perform the branch/followup/report sequence above and evaluate using
   `--require-barrier`. This additionally checks inherited helper identity and
   branch-specific completion. The helper gives up after 900 guest monotonic
   seconds; each client command and model turn is bounded to 180–200 seconds.

## Evidence boundaries and validation

Reports never contain account emails, tokens, auth payloads, raw account
responses, raw stderr, or prompts. Failed baseline acceptance can include at
most 1,200 characters of assistant explanation, with emails, bearer/API/JWT
tokens, secret assignments, and long opaque values scrubbed. Up to eight
configuration warnings receive the same treatment. Other diagnostics are
reduced to categories and counters. Each report carries at most 128 event rows.
Codex itself may write normal private session/log state in the isolated guest
home: do not export that directory as evidence. A provider stream recovery or
collision signal makes clean acceptance fail closed. Fixture tests must match
the host-owned test script digest, and the controller independently checks the
three expected transform results without relying on the fixture test script.

For a separate recovery experiment, collect and evaluate clean reports first.
Then close only the owned proxy's accepted upstream tunnels, call
`client.py recovery-followup` in each VM, and collect new reports. Evaluate these
with `--allow-upstream-recovery` (and `--require-barrier` when relevant). This
explicit mode accepts observed upstream recovery, reports its counters, requires
another correct context-recall turn, and still forbids controller/app-server
restarts or reconnecting their stdio pipes. Retain host proxy-fault evidence;
absence of a Codex warning does not prove a connection was reused. Maximum
budget is five model turns per inherited branch, including the active barrier
and this recovery followup.

`barrier-wait` timing out retains the original active turn for bounded transport
diagnosis; it does not interrupt that inherited turn. The VM runner must retain
the owned guests long enough to collect this evidence, then clean up the private
homes, disks, and snapshots. The generic persistent `relay.py` supports an
acknowledged `reset` of captured sockets without restarting the relay or Codex;
perform that reset in each child before releasing its egress gate.

The local unit tests are **stub/logic validation only**, not a real model or VM
acceptance pass. Run `python3 -m unittest -q` here. Generate version-matched
schemas with `codex app-server generate-json-schema --out /tmp/SCHEMA_DIR`, then
run `python3 validate_schema.py /tmp/SCHEMA_DIR`. This validates the request
shapes and catches differences from documentation examples. No credentials or
model calls are needed for either check. Only runner-collected reports plus
actual VM snapshot provenance can establish a real acceptance result.

Official protocol source: https://learn.chatgpt.com/docs/app-server (fetched
2026-09-05); local request schema: Codex CLI 0.153.4. In particular, the local
schema uses hyphenated `sandbox` values, despite camelCase examples in the page.
